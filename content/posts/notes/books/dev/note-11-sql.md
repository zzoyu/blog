### SQL 실행 과정

파싱과 최적화는 서로 구분짓지 않고 파싱/최적화로 퉁쳐서 부르는 경향이 있음

1. 파싱
  1. 파싱 트리 생성
  1. 구문 오류 확인 (syntax)
  1. semantic 체크
    1. 존재하지 않는 테이블/컬럼을 사용했는지
    1. 권한이 있는지 등 의미론적 오류 확인
1. 최적화
  1. Optimizer가 사전 수집된 통계 정보를 기반으로 다양한 실행 경로를 생성 → 가장 효율적인 하나를 선택.
  1. 최적 경로 탐색 알고리즘 같은 느낌인가? → 실제 그림은 최저 비용 신장 트리 같은 느낌인듯
  1. 근데 옵티마이저는 특별한 백그라운드 프로세스는 아니고 서버 프로세스가 가진 기능의 하나.
1. 로우 소스 생성
  1. 대충 컴파일과 같은 맥락
  1. 내부 코드 또는 프로시저로 변환


### 옵티마이저의 실행 계획

예상 실행 결과를 표시하는 것도 가능하고, 경로에 대한 랭킹을 표시하는 것도 가능함.

힌트를 제공해서 원하는 경로를 타도록 유도하는 것이 가능하다. 힌트는 러프하게 주는 것도, 세세하게 주는 것도 가능함. 덧붙여 옵티마이저 힌트를 사용할 때에는 가급적 `/*+ */`와 같이 주석 내부에서 사용하는 형태로 표기한다. 구문 오류 방지를 위함. 그 외 자잘한 문법적 주의사항들이 있음. 이건 각 DBMS마다 문법이 다를 수도 있으니 직접 확인하는 방향으로.

## 자주 사용하게 되는 힌트

- 최적화 목표는 `ALL_ROWS`, `FIRST_ROWS(N)`을 주로 사용
  - 이건 대충 어떤 의미인지 추측이 된다.
- 엑세스 방식은 `FULL`, `INDEX`, `INDEX_DESC`, `INDEX_FFS`, `INDEX_SS` 등이 있음.
  - 역순도 가능하다는 것은 몰랐음!
  - `FFS`와 `SS`는 뭘까?
    - Fast Full Scan
      > 인덱스 트리의 논리적 구조를 무시하고, 디스크에 저장된 인덱스 세그먼트 전체를 Multi-block I/O를 통해 물리적인 순서대로 빠르게 읽어들이는 스캔 방식

      한꺼번에 여러 블록을 조회하니 탐색 속도가 빠르지만 논리적 순서가 보장되지 않을 수 있다. (직접 정렬해주는 `order by`와 별개)

      기본적인 Index Full Scan은 B-Tree 인덱스의 리프들이 연결된 순서를 따라감.

      이걸 대량 데이터 색인 업무에서 이용할만한 아이디어가 하나 생각이 났기 때문에 제안해보아야 겠슨! → 인덱스로 설정한 컬럼만 가져올 때 가능한 거였고 무리였다…

    - Skip Scan
      > 결합 인덱스(두 개 이상의 컬럼이 사용된 인덱스)를 생성했을 때, 인덱스의 선두 컬럼이 `WHERE` 조건에 누락되었더라도 인덱스를 사용할 수 있게 해주는 기법. 선두 컬럼의 카디널리티가 낮고(예: '성별', '부서 코드'처럼 종류가 적음), 후행 컬럼의 카디널리티가 높을 때 매우 유용

      이게 무슨 의미인지 궁금해서 더 확인하였는데, 인공지능은 아래와 같은 예를 들어주었다.

      > `(성별, 나이)` 순서로 결합 인덱스가 있다고 가정해 보겠습니다. 쿼리가 `WHERE 나이 >= 30`이라면 선두 컬럼(성별)이 누락되었습니다. SS가 작동하면 DB는 내부적으로 선두 컬럼의 고유 값을 추출하여 `(성별='남' AND 나이 >= 30) OR (성별='여' AND 나이 >= 30)`처럼 치환한 뒤, 각 조건을 만족하는 구간만 점프하며 탐색합니다.

      PostgreSQL은 기본적으로 이 기능을 지원하지 않아, Bitmap Index Scan을 활용하는 등으로 우회된다고 하는데 팩트 체크는 필요하겠음.

- 조인 순서에 대한 힌트
  - `ORDERED`는 `FROM`에서 나열한 순서대로
  - `LEADING`은 힌트에서 지정한 순서대로
  - `SWAP_JOIN_INPUTS`는 “해시 조인 시, `BUILD INPUT`을 명시적으로 선택. 예)`SWAP_JOIN_INPUTS(T1)`” 이라고 적혀있는데 무슨 뜻인지 모르겠음!
- 조인 방식에 대한 힌트
  - `USE_NL` `USE_MERGE` `USE_HASH` `NL_SJ` `MERGE_SJ` `HASH_SJ`
  - 각 조인 방식의 차이점은 뭘까?
- 서브쿼리 팩토링
  - `MTERIALIZE`, `INLINE`  서브 쿼리로 지정한, 즉 `WITH`로 정의된 부분을 어떻게 처리할지에 관한 부분.
  - 물리적으로 생성하는 것과, 생성하지 않고 인라인으로 처리하는 것은 어떤 차이가 있을까?
- 쿼리 변환
  - `MERGE`
  - `NO_MERGE`
  - `UNNEST`
  - `NO_UNNEST`
  - `PUSH_PRED`
  - `NO_PUSH_PRED`
  - `USE_CONCAT`
  - `NO_EXPAND`
  → 솔직히 얘네들은 전부 모르겠다.

- 병렬 처리
  - `PARALLEL`
  - `PARALLEL_INDEX`
  - `PQ_DISTRIBUTE`
  → 이런 힌트가 있다는 것은 기본적으로는 병렬 처리를 하지 않는다는 걸까??

- 기타
  - `APPEND` 
  - `DRIVING_SITE`
  - `PUSH_SUBQ`
  - `NO_PUSH_SUBQ` 
  →  정말 듣도보도못한 ..
